> 时间仓促引起的架构实现债务,记录到这里,后续clean:
## Yoga 布局树每次更新都会全量创建并销毁，未利用持久化节点的增量布局能力。
当前每次布局都重新创建全部 YGNode、应用全部样式、计算整棵树并销毁，无法利用 Yoga 的脏标记、子树缓存和 Measure Cache。小规模示例可接受，但会增加大页面和高频更新的计算、分配成本。

## 增量渲染没有完整下发由布局变化连带影响的节点。
Core 虽然重新计算并暂存了全部节点布局，但增量 Mount 主要处理绑定目标、新增、删除和移动节点。文本尺寸变化可能影响父节点、兄弟节点及后续节点，这些节点的新布局可能未生成 SetHostLayout，存在平台 Host Tree 与 Core 布局不一致的风险。

## JS 与 Core 渲染权威共用同一线程，未拆分独立 JS 线程。
当前 JS executor 与 Core 建树/布局/事务同在一个线程串行，JS 重逻辑与渲染重计算会相互阻塞；因 JS↔Core 边界本就是事务消息，拆分 JS 独立线程成本低（守住 QuickJS 只在 JS 线程、渲染权威仍单点串行）。

## Feature 桥接退化为统一 invoke 分发器，未按设计做成 External Object 直调。
设计是 RN TurboModule 式：每个 Feature 暴露为一个 External Object、方法即 External Func，JS 拿到的对象直接锚定 native 实现——同步能力直接返回 JSValue，异步靠调用时直接持有的 JS 回调句柄回调，无统一分发器、无 module/method 字符串路由、无 requestId 查表。当前实现退回成单一 `featureRequest` external 入口 + payload 带 module/method 分发 + requestId 关联异步回传（等价于老式 bridge 的免序列化版），丢失了同步直返和方法级直接绑定的优势，也多了一层字符串路由与关联表开销。

## [✅已解决]Android 平台层用 Java 实现，未按设计采用 Kotlin。
设计要求 Android 平台层用 Kotlin；当前 runtime 层 11 个文件全为 Java（NativeGateway/RuntimeBridge/MountTransaction 等），gradle 也未配 Kotlin 插件——偏离设计意图。需迁移到 Kotlin（可 Kotlin/Java 混编逐步替换），JNI/C++ native 层不受影响。

## JS 响应式标脏靠遍历全部 binding，未建"字段→bindingId"反向索引。
create-reactive-page-vm 的 Proxy set 里遍历全部 bindings、逐个检查 deps 是否包含被改字段（O(M)，M=binding 总数），改一次 state 就扫一次全表。依赖关系编译期已静态确定，本应编译期一并产出 `字段名 → [bindingId]` 反向索引，set 时 O(1) 直取受影响 binding，无需运行时遍历。小页面可接受，binding 多时每次写都全表扫描，浪费。
