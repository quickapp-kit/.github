> 时间仓促引起的架构实现债务,记录到这里,后续clean:
## Yoga 布局树每次更新都会全量创建并销毁，未利用持久化节点的增量布局能力。
当前每次布局都重新创建全部 YGNode、应用全部样式、计算整棵树并销毁，无法利用 Yoga 的脏标记、子树缓存和 Measure Cache。小规模示例可接受，但会增加大页面和高频更新的计算、分配成本。

## 增量渲染没有完整下发由布局变化连带影响的节点。
Core 虽然重新计算并暂存了全部节点布局，但增量 Mount 主要处理绑定目标、新增、删除和移动节点。文本尺寸变化可能影响父节点、兄弟节点及后续节点，这些节点的新布局可能未生成 SetHostLayout，存在平台 Host Tree 与 Core 布局不一致的风险。

## JS 与 Core 渲染权威共用同一线程，未拆分独立 JS 线程。
当前 JS executor 与 Core 建树/布局/事务同在一个线程串行，JS 重逻辑与渲染重计算会相互阻塞；因 JS↔Core 边界本就是事务消息，拆分 JS 独立线程成本低（守住 QuickJS 只在 JS 线程、渲染权威仍单点串行）。
